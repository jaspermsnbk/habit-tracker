Phase 1

Account button and empty Settings page

All three screens build their own TopAppBar (HabitListScreen.kt:86, CalendarScreen.kt:91, TrendsScreen.kt:96). Replace those with one shared bar so the icon is identical and sits in the same place on every tab.

@Composable
fun HabitTopBar(title: String, onOpenSettings: () -> Unit) {
    TopAppBar(
        title = { Text(title) },
        actions = {
            IconButton(onClick = onOpenSettings) {
                Icon(Icons.Outlined.AccountCircle,
                     contentDescription = "Settings")
            }
        },
    )
}
  • Each screen gets an onOpenSettings: () -> Unit = {} parameter. The default keeps the existing screen tests compiling unchanged.
  • HabitApp holds var showSettings by rememberSaveable { mutableStateOf(false) }. When it's on, draw SettingsScreen(onBack) in place of the whole tab Scaffold, with no bottom bar. When it's off, draw the tabs as today.
  • BackHandler(enabled = showSettings) { showSettings = false } so system back closes Settings instead of leaving the app. The Settings top bar has a back arrow that does the same.
  • Wrap the tab content in rememberSaveableStateHolder(), keyed by tab name. Today, switching tabs throws away each screen's filters, month and range. Opening Settings would do the same to the current tab, and this fixes both.

Phases 2–5

What the Settings page holds

Account (phase 2)

SessionStore only knows "guest" today. Accounts are planned for Phase 4 of the app. For now, show where the data lives and hold a place for sign-in.

  • Row: "Guest", sub-line "Your habits are saved on this phone only."
  • "Sign in" button, disabled, with "Coming soon". Hide it entirely if you'd rather not show unfinished features (see open questions).
  • Leave out Sign out for now. For a guest it would just return to the landing screen with the data still there, which isn't what people expect "sign out" to mean.

Labels (phase 3)

Labels can be added from the Habits speed dial but never renamed or removed. No schema change is needed: habits.labelId already has onDelete = SET_NULL.

  • List each label with its habit count ("Fitness · 3 habits"). Tap a row to rename it; a delete icon asks for confirmation first: "Delete Fitness? Its 3 habits stay, just without a label."
  • "New label" row at the end reuses AddLabelDialog. Generalize it into LabelNameDialog(initialName, title, confirmText) so rename gets the same blank/duplicate checks.
  • DAO: updateLabelName(id, name), deleteLabel(id). Repository: renameLabel(id, name): Boolean, which skips the label itself in the duplicate check so changing only the capitalization works, plus deleteLabel(id). Add matching HabitViewModel methods.
  • Screens already fall back to "All labels" when the selected label disappears, so no changes are needed there.

Preferences (phase 4)

Store preferences in a new PreferencesStore, SharedPreferences-backed like SessionStore so no DataStore dependency is needed. It exposes a StateFlow<AppPreferences> and lives on HabitApplication.

  • Theme: System / Light / Dark. Dynamic color: on/off. MainActivity collects the flow and passes both into HabitTrackerTheme(darkTheme, dynamicColor), which already takes those parameters.
  • Week starts on: System default / Sunday / Monday / Saturday. Calendar and Trends currently call WeekFields.of(locale).firstDayOfWeek (TrendsScreen.kt:399 and the month grid). Provide the resolved day through a LocalFirstDayOfWeek CompositionLocal set in HabitApp, so neither screen needs a new parameter.
  • Trends opens on: 7D / 30D / 3M / 1Y, used as the first value of the range in TrendsScreen.
  • Show choices as single-choice dialogs with radio buttons, each row showing its current value, the standard Android settings pattern.

About (phase 5)

  • "Version 1.0". Read it from packageManager.getPackageInfo(packageName, 0).versionName, since buildConfig isn't enabled in app/build.gradle.kts.

Open questions

  • Show a disabled "Sign in" before accounts exist?It tells guests their data is local-only and that sign-in is coming. Hiding it avoids showing an unfinished feature. The plan shows it.
  • Offer "Delete all data" for guests?It's the only way to start fresh without reinstalling. It's destructive, so it needs a typed confirmation. Left out of this plan.
  • Is "Trends opens on" worth a setting?Remembering the last range used is an alternative with no settings row. Cut it if phase 4 feels crowded.

Before starting: the label filter for Trends is still uncommitted on master (TrendsScreen.kt, TrendsLabelFilterTest.kt). Commit it first so phase 1's top-bar edit to that file doesn't get mixed in.
